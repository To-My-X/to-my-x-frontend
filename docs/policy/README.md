# 서비스 정책

서비스 기획, 로직, 내부 규칙처럼 코드만으로 의도를 파악하기 어려운 정책 문서를 관리합니다. 정책이 확정되거나 변경되면 구현 여부와 별개로 먼저 기록합니다.

## 기록할 내용

- 서비스가 해결하려는 문제와 정책을 정한 이유
- 사용자별 권한, 노출 조건, 허용·제한 범위
- 계산·정렬·추천 로직의 입력, 단위, 경계값, 우선순위와 예외
- 데이터 유지·삭제, 상태 전환, 중복 처리 등 내부 규칙
- 다른 선택지를 사용하지 않은 이유, 변경 배경과 영향 범위

화면 하나에만 적용되는 정책도 기록할 수 있습니다. 코드에 드러난 조건을 옮기는 데 그치지 않고, 왜 그 조건이 필요한지 남깁니다. 확정되지 않은 값과 규칙은 미정 또는 제안으로 구분합니다.

## 정책과 통합 스펙의 관계

| 문서 | 역할 |
| --- | --- |
| `docs/policy/<주제>.md` | 서비스에 적용할 규칙과 그 의도·근거를 보존합니다. 구현 전에도 작성합니다. |
| `docs/specs/<주제>.md` | 관련 정책을 참조해 PRD·IA·Tech Spec과 완료 조건을 한 파일로 작성합니다. |

예를 들어 광고 노출 조건과 그 이유는 정책 문서에서 정의하고, 피드 화면에서 이를 적용하는 UI·데이터 처리·테스트는 통합 스펙에 작성합니다. 이는 구분을 설명하는 예시이며 광고 조건 자체를 확정한 것은 아닙니다.

- 정책 원본은 한 문서에서 관리합니다. 여러 스펙에서 같은 규칙을 복제하지 않고 해당 문서와 항목을 연결합니다.
- 정책을 구현하는 작업 자체도 하나의 통합 스펙이 될 수 있습니다. 이때도 규칙의 원본은 정책 문서에 둡니다.
- 모든 스펙에 새 정책 파일이 필요한 것은 아닙니다. 기존 정책을 활용하고, 순수한 화면 구성이나 기술 세부사항은 스펙에만 기록합니다.
- 정책만 확정되고 구현이 보류될 수도 있습니다. 명세 확정과 구현 완료를 구분합니다.
- 정책 변경 시 참조하는 스펙·코드·완료 조건의 영향을 함께 확인합니다.

## 작성과 변경 규칙

- 파일명은 주제를 나타내는 이름을 사용하고, 제목과 본문은 한국어로 작성합니다.
- 기획자·디자이너의 전달 자료, 사용자 결정, 에이전트의 해석을 구분합니다.
- 예시 이미지나 샘플 데이터만으로 권한·제한·수치를 확정하지 않습니다.
- 정책이 확정되거나 바뀌면 원본 문서를 먼저 갱신하고, 구현이 뒤따르면 관련 통합 스펙과 코드를 갱신합니다.
- 변경 이유와 확정 근거를 남깁니다. 단순 문구 수정은 Git 이력으로 관리합니다.
- 새 정책은 아래 목록에 등록합니다. 상태와 상세 규칙은 해당 문서에서 관리합니다.

## 작성 양식

필요한 항목을 사용하되, 의도·규칙·근거는 빠뜨리지 않습니다. 정책 문서에 PRD·IA·Tech Spec 양식을 강제하지 않습니다.

```markdown
# <정책 이름>

- 상태: 초안 / 확정 / 폐기
- 갱신일:
- 확정 근거: 결정 내용·확인일 또는 미정
- 관련 통합 스펙: 있으면 연결

## 목적과 배경

어떤 문제 때문에 이 정책이 필요한지 작성합니다.

## 적용 범위

대상 사용자, 기능, 화면, 데이터와 적용하지 않는 범위를 작성합니다.

## 정책 규칙

조건, 결과, 우선순위, 경계값, 예외를 작성합니다.

## 판단 근거

선택 이유와 고려한 대안, 미확정 사항을 작성합니다.

## 변경 영향

관련 정책·스펙·코드·데이터와 재검증할 항목을 작성합니다.

## 변경 기록

날짜, 바뀐 규칙과 이유, 확정 근거를 남깁니다.
```
