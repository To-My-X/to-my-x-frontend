# 커밋 컨벤션

Claude Code와 Codex를 포함해 이 저장소에서 커밋하는 모든 작업자가 따르는 규칙입니다.

## 기본 형식

```text
<type>: <작업 내용>
```

하나의 도메인이나 기능에 집중된 변경은 스코프를 붙일 수 있습니다.

```text
<type>(<scope>): <작업 내용>
```

## 타입

| 타입 | 사용 조건 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `chore` | 빌드, 의존성, 기타 유지보수 |
| `setting` | 프로젝트 설정, 환경 구성 |
| `docs` | 문서 추가 및 수정 |
| `test` | 테스트 코드 추가 및 수정 |
| `style` | 포맷팅, 코드 스타일 변경. 동작 변경 없음 |

화면 디자인이나 사용자에게 보이는 동작의 변경을 단순히 `style`로 분류하지 않습니다. 변경 목적에 맞춰 `feat`나 `fix` 등을 선택합니다.

## 스코프

- 변경이 하나의 도메인이나 기능에 집중될 때만 사용합니다.
- 여러 도메인에 걸친 작업은 스코프를 생략합니다.
- 현재 별도의 도메인 분류 문서는 없습니다. 관련 명세에서 확정한 기능 이름이 있으면 일관되게 사용하고, 아직 정해지지 않았다면 스코프를 생략합니다.
- 추후 도메인 분류를 문서화하면 그 목록을 기준으로 이 규칙을 갱신합니다.

## 커밋 분리

- 한 커밋은 하나의 목적을 가집니다. 서로 관계없는 기능, 설정, 문서 변경은 목적별로 나눕니다.
- 예를 들어 로그인 기능, 빌드 환경 구성, 하네스 문서 추가는 각각 별도 커밋 대상입니다.
- 기능 변경과 그 기능의 명세·테스트 갱신처럼 같은 목적의 변경은 함께 커밋합니다.
- 커밋 전 diff를 확인하고, 관련 파일이나 변경 구간만 선별해서 스테이징합니다.
- 같은 파일에 여러 목적의 변경이 섞여 있어 안전하게 분리하기 어렵다면 예외적으로 함께 커밋할 수 있습니다. 이때 중심이 되는 목적의 타입과 메시지를 사용하고, 함께 포함한 이유를 본문에 남깁니다.
- 사용자가 단순히 커밋을 요청해도 독립적인 목적이 여러 개라면 에이전트가 목적별로 나눕니다.

## 메시지 작성

- 타입과 스코프는 정해진 표기를 사용하고, 작업 내용과 본문은 한국어로 작성합니다.
- `추가했다`보다 `추가`, `수정했다`보다 `수정`처럼 현재형으로 간결하게 씁니다.
- 제목에는 변경 내용을 구체적으로 적고, 필요한 경우 본문에 변경 이유를 설명합니다.
- 본문이 있으면 제목과 한 줄 띄고 작성합니다.
- 실제 수행하지 않은 검증이나 구현을 완료한 것처럼 적지 않습니다.

## 예시

```text
setting: 하네스 엔지니어링 초기 구조 구성
feat: 피드 화면과 세로 페이지 이동 추가
fix: 화면 밖 영상이 계속 재생되는 오류 수정
refactor: 피드 데이터 변환 로직 분리
docs: 커밋 컨벤션과 문서 목록 추가
chore: 영상 재생 라이브러리 추가
test: 피드 로딩 실패 처리 검증 추가
style: 컴포넌트 들여쓰기 정리
```

## 커밋 전 확인

1. [문서 동기화](../harness/documentation-sync.md)를 수행합니다.
2. `git status --short --branch`, `git diff`, `git diff --cached`로 기존 변경과 스테이징할 내용을 확인합니다. 새 파일은 내용도 직접 읽습니다.
3. 변경을 목적별로 분류하고 관련 코드, 명세, 테스트를 함께 스테이징합니다.
4. 필요한 검증 결과를 확인하고 실패·미실행 항목을 보고합니다.
5. `git diff --cached --check`와 스테이징된 diff를 확인한 뒤 규칙에 맞는 메시지로 커밋합니다.

문서에 규칙을 추가하는 것만으로 커밋이나 푸시를 실행하지는 않습니다. 사용자가 요청한 작업 범위에 따라 수행합니다.
