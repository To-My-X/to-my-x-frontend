# 브랜치 운영 규칙

1인 개발에서는 `main`과 `develop` 두 브랜치를 유지합니다. 일반 개발과 내부 테스트는 `develop`에서 진행하고, 오래 걸리거나 테스트를 방해하는 작업만 임시 브랜치로 분리합니다.

## 브랜치 역할

| 브랜치 | 역할 | CI/CD 연결 계획 |
| --- | --- | --- |
| `main` | 검증된 프로덕션 배포 코드 | 검사 후 프로덕션 배포 |
| `develop` | 일반 개발 커밋 누적과 내부 테스트 | 검사 및 내부 테스트 배포 |
| `feat/<작업명>`, `fix/<작업명>` | 필요할 때만 만드는 임시 작업 브랜치 | 검사 |

Codex 환경에서 임시 브랜치에 `codex/` 접두사가 필요하면 `codex/feat/<작업명>`, `codex/fix/<작업명>`을 사용합니다. 상시 브랜치 이름은 `main`, `develop`으로 유지합니다.

## 일반 개발과 배포

1. 작업 전 현재 브랜치와 미커밋 변경을 확인합니다. 일반 개발은 `develop`에서 바로 커밋합니다.
2. 내부 테스트 중인 상태를 유지하면서 다음 기능을 개발하거나 위험한 변경을 진행할 때는 `develop`에서 임시 브랜치를 만듭니다.
3. 임시 작업은 필요한 검증과 문서 갱신을 마친 뒤 `develop`에 병합합니다. 병합된 임시 브랜치는 정리합니다.
4. 내부 테스트를 마친 변경은 `develop → main` PR로 배포 범위와 검증 결과를 확인하고 반영합니다. AI 리뷰 결과도 이때 활용할 수 있습니다.
5. 장기 유지하는 두 브랜치의 이력을 연결하도록 배포 PR은 merge commit 방식으로 병합합니다. `main` 반영 후에는 `main`을 `develop`에 병합해 기준을 맞춥니다.

`main`에는 일반 개발 커밋을 직접 쌓지 않습니다. 브랜치 이동이나 병합 때문에 기존 미커밋 작업을 버리지 않습니다.

## 프로덕션 긴급 수정

- 최신 `main`에서 `fix/<작업명>`을 만들고 필요한 수정과 검증을 진행합니다.
- PR로 `main`에 반영한 뒤 `main`을 `develop`에도 병합합니다. 진행 중인 임시 브랜치에는 필요에 따라 최신 `develop`을 반영합니다.
- 다음 배포에서 긴급 수정이 사라지지 않도록 양쪽 브랜치의 반영 여부를 확인합니다.

## CI/CD 적용 범위

[빌드와 배포 명세](../specs/build-deploy.md)를 따릅니다. develop 반영 후 웹 테스트 배포, main 반영 후 웹 프로덕션 배포를 자동 실행합니다. 직접 push도 같은 자동화를 실행합니다. 앱 빌드·제출은 [app-release 스킬](../skills/app-release/SKILL.md)로 요청한 시점에 수행합니다.

워크플로 파일은 구성하되 실제 활성화에는 Expo 토큰과 Hosting·서명·스토어 초기 설정이 필요합니다. 브랜치 보호와 필수 검사 설정은 아직 구성하지 않았습니다.

## 커밋과 빌드 전

[커밋 컨벤션](commit.md)과 [문서 동기화 리뷰 스킬](../skills/documentation-review/SKILL.md)을 따릅니다. 브랜치 생성이나 규칙 기록만으로 푸시·PR 생성·병합·배포를 수행하지 않으며, 사용자가 요청한 범위에서 진행합니다.
