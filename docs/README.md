## 문서 구분

- `policy/`: 서비스 규칙과 그 이유, 기획 의도, 계산 로직, 예외와 내부 판단 기준을 기록합니다.
- `specs/`: 정책·화면·기능·사용자 흐름별로 PRD·IA·Tech Spec을 통합합니다. 관련 정책을 참조해 구현과 검증을 구체화합니다.
- `conventions/`: 코드 작성과 협업 규칙. 현재는 커밋·브랜치 규칙을 관리하며, 다른 규칙은 필요할 때 추가합니다.
- `harness/`: 에이전트 운영, 문서 동기화, 실수 기록과 인수인계.
- `skills/`: 프로젝트 공통 스킬 원본과 목록. 에이전트별 탐색 폴더에는 원본을 가리키는 링크를 둡니다.
- `setup/`: SDK·로컬 실행 환경과 설치·빌드 준비 절차를 관리합니다.
- `references/`: 전달받은 자료의 고정 스냅샷과 출처를 보관합니다. 현재 정책·구현 기준은 `policy/`와 `specs/`에서 관리하며 과거 스냅샷을 수정해 새 결정으로 바꾸지 않습니다.

PRD, IA, Tech Spec을 별도 폴더나 파일로 나누지 않습니다. 같은 주제의 기획·흐름·구현 설계는 `specs/`의 한 파일에서 갱신합니다. 정책 원본은 `policy/`에서 관리하며 스펙에서 중복 정의하지 않습니다. 제품 작업은 [제품 명세 총괄](specs/product-overview.md)에서 시작합니다. 전달 자료의 요구사항과 제안·미결정 사항을 구분했으며 제품 구현과 기능 QA는 미착수입니다.

## SDD 진행 방식

**통합 스펙 작성·확인 → 구현 계획 → 구현 → 완료 조건 검증 → 문서 동기화** 순서로 진행합니다.

- 기획자·디자이너가 전달한 자료와 사용자 결정을 통합 스펙에 정리합니다. 전달된 자료, 확정 사항, 제안, 가정을 구분합니다.
- 구현 전에 해당 범위의 목적, 정책, 흐름, 구현 설계와 완료 조건을 확인합니다. 미확정 사항에 의존하는 구현을 임의로 진행하지 않습니다.
- 변경 시 해당 문서의 기획·IA·기술 설계가 함께 맞는지 확인합니다. 구현 결과를 정당화하려고 요구사항을 바꾸지 않습니다.
- 검증은 완료 조건과 연결해 명령어·결과·플랫폼을 기록합니다. 미실행·실패·환경 차단을 통과와 구분합니다.
- 정책 변경은 구현 여부와 별개로 정책 원본에 먼저 기록하고, 영향을 받는 통합 스펙도 함께 갱신합니다.
- 인수인계에는 현재 상태와 다음 작업을 남기고, 상세 내용은 정책과 통합 스펙을 연결합니다.

## 문서 추가와 변경

새 정책은 [정책 문서 목록](policy/README.md), 새 통합 스펙은 [스펙 목록](specs/README.md)에 등록합니다. 다른 운영 문서와 컨벤션은 이 문서의 목록에 등록합니다. 상세 정책을 여러 목록에 복제하지 않습니다.

컨벤션에는 적용 범위, 규칙, 필요한 예시를 적습니다. 아직 결정하지 않은 규칙을 미리 확정하지 않으며, 기존 규칙을 바꾸면 관련 코드·문서와의 차이도 확인합니다.
