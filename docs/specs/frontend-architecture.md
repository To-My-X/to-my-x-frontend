- 유형: 공통 구조·기술 설계
- 명세 상태: 확정
- 구현 상태: 설계 기준 적용, 기존 템플릿 코드 전환은 미착수
- 갱신일: 2026-10-20
- 확정 근거: 사용자가 기능별 구성과 UI·데이터 처리 분리를 채택하고 저장소 문서로 관리하도록 요청했습니다.
- 관련 문서: [공통 지침](../../AGENTS.md), [통합 스펙 관리](README.md)

## 목적과 범위 — PRD

웹·Android·iOS에서 코드를 공유하면서 기능의 UI, 상태, 데이터 접근 책임을 구분합니다. Claude와 Codex는 새 기능을 구현하거나 기존 기능을 수정하기 전에 이 문서와 해당 기능의 통합 스펙을 읽습니다.

기능별 폴더를 기본으로 사용합니다. 클린 아키텍처의 책임 분리 원칙은 활용하되, 모든 요청에 Repository 인터페이스·구현체·UseCase·DI 컨테이너를 만들지는 않습니다. 엄격한 FSD 계층이나 멀티패키지 구조도 현재 도입하지 않습니다.

이번 결정은 설계 규칙의 확정입니다. 기존 화면 이동·파일 일괄 이동·의존성 설치는 포함하지 않습니다. 서비스 정책과 실제 화면 동작은 별도 정책·기능 스펙에서 정의합니다.

## 구성과 흐름 — IA

아래 구조는 배치 예시이며 아직 존재하지 않는 폴더와 기능을 포함합니다. 필요한 파일이 생길 때만 폴더를 만듭니다.

```text
src/
├── app/                     # Expo Router 라우트·레이아웃·화면 연결
├── features/
│   └── feed/                # 예시 기능
│       ├── FeedScreen.tsx
│       ├── components/      # 기능 전용 UI
│       ├── hooks/           # 화면 상태·데이터 요청 조합
│       ├── api/             # 요청·응답 계약과 데이터 접근
│       ├── domain/          # 복잡한 정책·계산이 있을 때만 추가
│       └── types.ts         # 기능 안에서 공유하는 타입
├── components/              # 여러 기능이 공유하는 UI
├── lib/                     # HTTP·저장소 등 공통 기반
└── theme/                   # 색상·폰트·간격 등 디자인 토큰
```

기본 흐름은 `라우트 → 기능 화면 → 훅 → 기능 API → 공통 클라이언트`입니다. 간단한 화면에 각 단계를 강제로 만들지 않습니다. 복잡한 정책·계산은 기능의 domain에서 처리하고, 훅이나 API 조합 코드가 이를 사용합니다.

## 기술 설계 — Tech Spec

### 라우팅과 화면

- `src/app/`에는 라우트, `_layout.tsx`, 내비게이션 연결과 라우트 매개변수 처리를 둡니다. 제품 화면 본문은 기능의 화면 컴포넌트로 분리합니다.
- 기능 화면은 가능한 한 props와 콜백으로 입력을 받습니다. 파일 경로·URL 해석이 UI 전체에 퍼지지 않도록 라우트 진입점에서 처리합니다.
- 공통 Provider는 루트 레이아웃에서 조합하되, 초기화 코드가 커지면 `src/app/` 밖의 모듈로 분리합니다.

### 의존성 방향

| 위치 | 참조할 수 있는 대상 |
| --- | --- |
| app | features, components, lib, theme |
| features의 한 기능 | 같은 기능 내부, components, lib, theme |
| components | 다른 공통 컴포넌트, lib, theme |
| lib | 다른 공통 기반 코드. 기능·UI·라우트에는 의존하지 않음 |
| theme | 디자인 토큰과 테마 정의. 기능·라우트에는 의존하지 않음 |

- 기능끼리 직접 import하거나 순환 참조하지 않습니다. 두 기능의 연결은 라우트나 상위 조합 지점에서 props·콜백으로 처리합니다. 공통 책임이 실제로 확인되면 공유 위치를 정합니다.
- 여러 기능이 쓰는 비즈니스 개념이 필요해지면 기능 스펙에 소유 위치와 의존성 방향을 먼저 정합니다. 이를 HTTP 도구와 섞어 lib에 넣지 않습니다.
- 기능 내부 구현은 내부에서 직접 참조합니다. 모든 폴더에 index.ts를 만들 필요는 없습니다. 외부에서 쓰는 진입점이 늘어나면 공개할 항목만 정리합니다.
- 폴더는 Gradle 모듈 같은 강제 경계가 아닙니다. 현재는 코드 리뷰로 준수 여부를 확인하며, import 제한을 자동 검사하는 도구는 구성하지 않았습니다.

### UI·상태·데이터

- 화면·표시용 컴포넌트에서 HTTP 요청을 직접 실행하지 않습니다. 기능 API가 요청·응답과 오류 변환을 담당하고, 훅이 로딩·오류·재시도와 UI의 연결을 담당합니다.
- 서버 데이터와 UI 상태를 구분합니다. 서버 응답을 전역 UI 저장소에 중복 보관하지 않습니다. 캐시·재요청·무한 페이지 처리가 필요하면 기능 스펙에서 서버 상태 도구를 결정합니다.
- 입력값·모달·현재 선택처럼 화면에 한정된 상태는 로컬 상태로 시작합니다. 여러 화면에서 함께 소유해야 할 때만 상태를 올리거나 전역 저장소를 검토합니다.
- 훅은 상태와 부수 효과를 조합하는 수단입니다. ViewModel과 동일한 수명주기·책임을 가진다고 가정하지 않으며, 모든 화면에 훅 하나를 의무적으로 만들지 않습니다.
- 서버 응답 타입과 화면 모델이 다르면 기능 안에서 변환합니다. 실제 외부 입력의 검증·실패 처리는 유지합니다. 타입 선언만으로 런타임 검증이 된다고 가정하지 않습니다.
- React에 의존하지 않는 복잡한 정책·계산은 순수 TypeScript 함수로 분리합니다. Repository·UseCase는 데이터 소스 분리나 복잡한 흐름이라는 구체적인 필요가 있을 때 도입하고 이유를 스펙에 기록합니다.
- 서버 상태·전역 상태·폼 라이브러리는 이번 결정으로 확정하거나 설치하지 않습니다.

### 공유 UI와 플랫폼 차이

- 기능 전용 UI는 해당 기능에 둡니다. 여러 기능이 같은 책임으로 사용할 때 공통 components로 옮깁니다. 모양만 비슷한 컴포넌트를 억지로 합치지 않습니다.
- 공통 색상·폰트·간격은 디자인 토큰을 사용합니다. 기능별 배치 수치까지 모두 전역 토큰으로 만들지는 않습니다.
- 웹·네이티브는 공통 구현을 우선하며, 실제 차이가 있을 때 `.web.tsx`, `.native.tsx`, `.ios.tsx`, `.android.tsx` 등 플랫폼 파일로 분리합니다. 공통 import 경로에서 플랫폼 구현을 선택할 수 있게 유지합니다.
- 피드의 영상 재생·화면 밖 자원 해제·페이지 전환·무한 로딩 정책은 피드 스펙에서 정의합니다. 이 폴더 구조만으로 플랫폼 성능이 보장되지는 않습니다.

### 기존 코드 적용

현재는 Expo 템플릿 화면이 `src/app/index.tsx`, `src/app/explore.tsx`에 있고 공통 코드가 components·hooks·constants에 있습니다. 설계 문서가 생겼다는 이유로 이 파일들을 일괄 이동하지 않습니다.

- 새 제품 기능부터 features 구조를 적용합니다.
- 기존 템플릿 화면을 제품 화면으로 대체할 때 화면 본문과 전용 코드를 해당 기능으로 옮깁니다.
- `src/constants/theme.ts`와 기존 공통 hooks 등은 우선 유지합니다. theme 구조를 도입할 때 기존 정의를 옮기고 참조를 갱신하며 중복 원본을 남기지 않습니다.
- 이전 구조와 새 규칙이 충돌하면 작업하는 범위에서 정리하고, 남은 범위를 기능 스펙이나 인수인계에 기록합니다.

## 완료 조건과 검증

새 기능의 구현·리뷰에서는 다음을 확인합니다.

- 기능별 파일 위치와 의존성 방향이 이 문서에 맞고 순환 참조가 없는가?
- 라우트와 제품 화면, HTTP 접근과 UI 책임이 분리돼 있는가?
- 서버 데이터와 UI 상태의 소유자가 명확하고 불필요한 중복 상태가 없는가?
- 복잡한 정책·계산을 분리했다면 경계값·실패 조건을 검증했는가?
- 플랫폼 차이와 미검증 환경을 스펙에 남겼는가?
- lint·타입 검사와 해당 변경에 필요한 동작 검증을 통과했는가?

현재 완료 범위는 설계 원본과 에이전트 진입점 연결입니다. 기존 코드 전환, import 규칙 자동 검사, 라이브러리 선정은 완료 범위가 아닙니다. 설계 예외가 필요하면 이유·영향·적용 범위를 작업 스펙에 기록하고, 공통 규칙 자체를 바꿀 때는 이 원본도 함께 갱신합니다.
