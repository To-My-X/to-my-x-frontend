# 통합 스펙

정책·화면·기능·사용자 흐름을 구현하기 위한 PRD·IA·Tech Spec을 주제별 한 파일로 관리합니다. 서비스 규칙과 그 이유는 [정책 문서](../policy/README.md)에 기록하고, 통합 스펙은 해당 정책을 참조해 구현 범위와 검증 방법을 구체화합니다.

## 한 주제, 한 문서

PRD·IA·Tech Spec은 문서 안의 관점이며 별도 산출물로 나누지 않습니다. 문서 단위는 정책, 화면, 기능, 사용자 흐름 중 작업 목적에 맞게 선택합니다. 모든 내용을 거대한 파일 하나에 넣는 방식도 아닙니다.

예를 들어 피드 화면, 공감 기능, 광고 노출 정책은 각각 독립적인 주제가 될 수 있습니다. 이는 문서 단위의 예시이며 현재 확정된 제품 요구사항은 아닙니다.

- 파일은 `docs/specs/<주제>.md`에 만들고, 제목과 본문은 한국어로 작성합니다.
- [통합 스펙 양식](_template.md)을 복사해 작성합니다. 양식 자체는 제품 명세가 아닙니다.
- 화면이 없는 정책도 같은 양식을 사용합니다. IA에는 영향을 받는 정보·처리 흐름을 적거나, 해당하지 않는 이유를 명시합니다.
- 구현이 아직 없는 기획도 기록할 수 있습니다. 기술 설계나 API가 미정이면 미정으로 표시하며 임의로 채우지 않습니다.
- 문서 유형이 둘 이상이어도 파일을 나누지 않고 유형에 함께 표시합니다.
- 서비스 정책의 원본은 `docs/policy/`에 둡니다. 공통 규칙뿐 아니라 한 화면에만 적용되더라도 의도와 근거를 보존해야 하는 서비스 규칙은 정책 문서로 관리합니다.
- 통합 스펙에는 관련 정책 문서와 항목을 연결하고, 해당 작업의 화면 흐름·기술 설계·완료 조건을 적습니다. 정책 본문을 다시 정의하지 않습니다.
- 모든 작업에 정책 파일을 새로 만들 필요는 없습니다. 기존 정책을 활용하고, 순수한 UI 구성이나 기술 세부사항은 스펙에서 관리합니다.

## 문서가 답해야 할 질문

| 관점 | 기록할 내용 |
| --- | --- |
| PRD | 누구의 어떤 문제를 해결하는가? 포함·제외 범위와 정책의 이유는 무엇인가? |
| IA | 어디에서 진입하며 정보와 화면은 어떻게 구성되는가? 입력·상태·다음 단계는 무엇인가? |
| Tech Spec | 어떤 데이터, 상태, API, 컴포넌트와 알고리즘으로 구현하는가? 플랫폼 차이와 실패 처리는 무엇인가? |
| 검증 | 어떤 조건을 만족해야 완료인가? 무엇을 실제로 확인했고 무엇이 남았는가? |

내부 계산 규칙의 조건과 선택 이유는 정책 문서에서 확인합니다. 통합 스펙에는 이를 구현할 알고리즘과 경계값 검증을 적습니다. 근거가 없는 숫자나 조건은 미정으로 남깁니다.

## 기획·디자인 자료에서 명세로

1. 전달받은 자료의 이름, 버전·날짜, 확인 가능한 위치를 기록합니다. 외부 자료의 링크는 실제 입력 근거를 추적할 필요가 있을 때 사용합니다.
2. 자료에 명시된 사실과 에이전트의 해석을 구분합니다. 예시 데이터·이미지·선택 상태를 서비스 제약으로 확정하지 않습니다.
3. 빈 상태, 로딩, 오류, 권한, 취소·뒤로 가기, 접근성 등 빠진 조건은 미결정 사항으로 남깁니다.
4. 기획·디자인 담당자는 제품 의도와 화면 동작을, 개발 담당자는 기술 설계를 검토하는 관점으로 같은 파일을 갱신합니다. 실제 확인 없이 담당자 이름이나 확정 근거를 만들지 않습니다.
5. 구현할 범위가 확정되면 그 범위와 완료 조건을 기준으로 개발합니다. 확인되지 않은 나머지는 계속 미정으로 남깁니다.

## 상태와 변경 관리

- 명세 상태는 `초안`, `확정`, `폐기`로 표시하고, 구현 상태는 `미착수`, `진행 중`, `완료`로 따로 표시합니다.
- 검증 상태는 `미실행`, `일부 확인`, `통과`, `실패`, `환경 차단`으로 구분합니다. 플랫폼별 결과가 다르면 각각 기록합니다.
- 일부 항목만 확정되면 문서 전체를 확정으로 바꾸지 않고, 확정된 구현 범위를 명시합니다.
- 정책이 바뀌면 정책 원본에 이유와 확정 근거를 기록하고, 영향을 받는 통합 스펙의 흐름·설계·완료 조건을 함께 갱신합니다.
- 변경한 완료 조건은 다시 검증합니다. 과거의 통과 결과를 새 정책에 그대로 적용하지 않습니다.
- 구현 결과가 명세와 다르면 원인을 확인하고, 명세 오류인지 구현 오류인지 구분합니다.
